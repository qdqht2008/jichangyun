# 网站流量优化 P1 第二批：机场评测证据门设计

## 背景与目标

P1 第一批已经用统一的静态评测结构改造大哥云、肥猫云和精灵学院，并通过零依赖 Node 审计。第二批继续保持纯 Cloudflare Pages 静态架构和现有暖色编辑型视觉，候选页限定为飞鸟云、瞬云和红杏云。

本批目标：

- 把三张旧式宣传页改造成来源、判断边界和购买限制清晰的评测页。
- 继续区分商家资料、第三方记录与编辑判断，不把公开资料写成本站亲测。
- 以“当前商家套餐已核验”为逐页实施前置条件，避免用旧截图或第三方价格冒充官网现价。
- 逐页实施、逐页验证；任何一页证据不足时暂停该页，不用猜测补齐，也不阻塞已满足证据门的页面。

- 故障排查长尾、客户端教程及 P2/P3 项目。
- 推送、部署和分析事件。

## 方案选择

采用“固定三页候选 + 逐页证据门 + 共享语义结构 + 静态审计”。设计范围包含三页，但每页只有在证据门完成后才能进入该页的 RED/GREEN 实施循环。

不采用以下方案：

- 只做一页：证据风险最低，但无法建立第二批横向一致性。
- 直接使用第三方套餐：速度更快，但不满足当前商家套餐核验要求。

## 逐页证据门

每页开始写测试或正文前，必须形成一份事实基线，至少包含：

1. 当前商家套餐页的文字或截图，能够识别套餐名、价格、周期、流量及明确限制。
2. 当前商家入口可访问或能由商家页面、当前入口配置确认品牌身份。
3. 至少一个带更新时间的第三方来源，用于交叉核对套餐状态或提供延伸阅读。
4. 若引用具体性能数字，第三方记录必须同时给出测试日期、网络环境和测试工具。
5. 冲突数据必须明确择一：以更新且更接近商家原始页面的材料为准，另一版本记录为冲突，不做平均或拼接。

若缺少第 1 项，该页不得制作价格表、更新套餐事实测试或进入正文重构。允许继续整理来源和冲突清单，但不能以第三方价格替代商家当前资料。

## 内容结构

三页复用第一批已有 class 和以下顺序：

1. 标题与中性摘要。
2. 编辑信息：作者、审核方式、最后核验日期。
3. 一句话结论与资料边界。
4. 适合与不适合人群。
5. 可核验优点与限制。
6. 当前套餐文字表格。
7. 线路、协议、客户端与解锁资料说明。
8. 购买与使用风险。
9. 商业 CTA。
10. 信息来源、冲突说明与更新时间。

统一资料边界文案：

> 本文仅整理公开资料，实际体验因地区、运营商、设备和时段而异。

页面不显示推广或佣金披露；商业 CTA 必须继续使用 `rel="sponsored nofollow noopener"`。

## 编辑规则

- 当前套餐表只使用完成证据门后的商家资料；第三方数据只用于交叉核对并明确归因。
- 商家声明的线路、解锁、不限速、设备数量、客服响应和安全性均使用“商家资料显示”或“商家标注”。
- 适合人群、限制和购买建议只能从价格周期、流量、设备、退款、客户端或地区限制推导。
- 不新增运营年限、稳定率、解锁率、用户规模、峰值速度或安全承诺。
- 删除正文、FAQ、description、Open Graph、Twitter 与 JSON-LD 中无法支持的“高速稳定”“全解锁”“理想选择”等确定性结论。
- 不设置评分、星级或排名。
- 旧套餐截图可在当前文字表格完成后删除；不得继续作为现价依据。

## 聚合页与 SEO

`jichang/index.html` 只更新本批实际完成证据门并实施的卡片：

- 添加与详情页一致的中性摘要和核验日期。
- 保持卡片顺序不变。
- 不修改未实施页面的正文。

详情页：

- Article 作者统一为“优质机场推荐编辑部”。
- `dateModified` 与页面实际核验日期一致，不伪造 `datePublished`。
- FAQ 只保留由当前套餐或明确商家规则支持的问题。
- Sitemap 只更新实际修改页面；证据门未完成的页面不得提前更新 `lastmod`。

## 视觉与架构

第一批已提供 `.review-meta`、`.review-verdict`、`.review-audience`、`.review-pros-cons`、`.plan-table-wrap`、`.review-risk` 和 `.review-sources`。第二批优先直接复用，不引入模板、框架、依赖、运行时正文注入或新的视觉体系。

仅当新增的“来源冲突”状态无法由现有风险块和来源列表清晰表达时，才允许在 `css/main.css` 增加一个最小修饰类。移动端继续要求双栏折叠、表格仅在容器内滚动、整页无横向溢出。

## TDD 与实施顺序

每页独立执行：

1. 完成该页事实基线并记录来源日期。
2. 在 `tests/site-audit.test.mjs` 增加该页的结构、关键事实、陈旧文案和 CTA 意图测试。
3. 运行测试，确认新增断言按预期失败。
4. 只重构该详情页，使该页测试转绿。
5. 更新对应聚合页卡片和 Sitemap 日期。
6. 运行完整审计和空白检查，再进入下一页。

默认顺序：飞鸟云 → 瞬云 → 红杏云。若前一页证据门未完成，可跳到已补齐证据的下一页；跳过必须明确记录，不得宣称整批完成。

## 验收标准

- 三页或实际完成的子集保持纯静态，并复用第一批评测结构。
- 每个已实施页面都有可追溯的商家套餐事实基线和第三方交叉来源。
- 商家、第三方与编辑判断边界清晰，不出现本站亲测暗示。
- 旧截图、旧优惠和无证据确定性结论从正文与元数据同步清理。
- 商业 CTA 属性保持正确。
- 未完成证据门的页面、卡片和 Sitemap 日期不被修改。
- `node --test tests/site-audit.test.mjs` 零失败、零跳过。
- `git diff --check` 无错误，并通过桌面与 390px 浏览器验证。
- 不推送、不部署，除非用户另行明确要求。

在执行各页面的测试与正文修改任务前，需要用户提供或确认以下当前商家资料：

- 飞鸟云套餐页文字或截图。
- 瞬云套餐页文字或截图。
- 红杏云套餐页文字或截图。

资料可以逐页提供。实施计划先安排事实基线检查，再安排对应页面的 RED/GREEN 任务；未提供资料的页面停在事实基线检查，不会用第三方套餐替代，也不会提前修改页面。
