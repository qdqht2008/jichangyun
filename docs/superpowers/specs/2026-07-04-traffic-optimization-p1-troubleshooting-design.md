# 网站流量优化 P1：故障排查长尾内容设计

## 背景与目标

现有 `guide/frequent-disconnections/` 已覆盖节点、网络、客户端、订阅和设备五类原因，但内容停留在通用建议层，没有按用户看到的症状分流，也缺少官方来源、错误信息对照、安全恢复步骤和相关教程入口。

本批目标是用一个排查入口和两篇症状型长尾页覆盖三类不同搜索意图：

- Clash 连不上或频繁断线；
- Clash 订阅更新失败；
- Clash 显示已连接或能测延迟，但应用仍无法上网。

本批保持纯 Cloudflare Pages 静态架构、现有暖色编辑型视觉和外科手术式修改，不扩展到客户端教程全面更新、P2 图标或部署工作。

## 已确认范围

修改：

- `guide/frequent-disconnections/index.html`
- `guide/index.html`
- `sitemap.xml`
- `tests/site-audit.test.mjs`

新增：

- `guide/subscription-update-failed/index.html`
- `guide/connected-but-no-internet/index.html`

仅在现有样式无法清楚表达诊断流程和错误对照表时，才对 `css/main.css` 增加最小共享样式。默认不修改教程正文、导航脚本、机场评测页和部署配置。

## 方案选择

采用“一个排查入口 + 两篇症状详情页”。

没有采用仅新增两篇页面的方案，因为旧断线页仍会保留宽泛且容易误导的排查顺序；没有采用单篇超长指南，因为订阅错误和流量接管错误属于不同搜索意图，混在一页会增加阅读成本并弱化标题相关性。

## 内容架构

### 1. 故障分流入口

路径：`/guide/frequent-disconnections/`

目标搜索意图：Clash 连不上、节点全部超时、频繁断线、退出后仍断网。

页面改造成“5 分钟故障分流入口”，先让读者识别症状，再进入最短可逆检查：

1. 没有节点或订阅更新报错：进入订阅更新失败页。
2. 节点有延迟但网页打不开：进入已连接但无法上网页。
3. 只有一个或少数节点失败：切换节点，并参考节点速度差异页。
4. 全部节点超时：对比不同网络，检查账号、节点和客户端日志。
5. 仅部分应用失败：区分系统代理与 TUN 的流量接管范围。
6. 退出客户端后仍断网：恢复系统代理设置，再停止继续叠加改动。

入口页不复制两篇详情页的完整步骤，只展示症状、首个安全动作和下一页链接。

### 2. 订阅更新失败页

路径：`/guide/subscription-update-failed/`

目标搜索意图：Clash 订阅更新失败、订阅超时、401、403、无法解析、配置验证失败。

内容顺序：

1. 区分“订阅无法下载”和“下载后无法解析”。
2. 检查账号状态、套餐有效期和商家后台最新订阅链接。
3. 用另一网络测试订阅服务器是否可达。
4. 检查客户端和 Mihomo 内核是否支持当前配置字段或协议。
5. 按错误类型解释下一步：
   - 401/403：账号、授权或链接状态；
   - timeout/network error：当前网络到订阅服务器不可达；
   - parse/config validation：内容格式或客户端兼容问题；
   - 更新成功但无节点：配置内容、筛选或商家端输出异常。
6. 查看日志并向商家提交经过脱敏的信息。

页面不推荐来历不明的订阅转换站，也不展示真实订阅 URL、令牌或节点地址。

### 3. 已连接但无法上网页

路径：`/guide/connected-but-no-internet/`

目标搜索意图：Clash 已连接但不能上网、节点有延迟却打不开网页、系统代理或 TUN 开启后没网。

按数据路径排查：

1. 订阅是否存在节点；
2. 当前节点是否可建立连接；
3. 应用流量是否由系统代理或 TUN 接管；
4. 规则模式下目标请求是否误走直连；
5. 日志是否显示 DNS 解析、连接或规则错误；
6. 是否存在浏览器代理扩展、其他 VPN、加速器或本地端口冲突。

页面必须明确：延迟测试成功只说明测试请求获得响应，不证明目标应用的实际流量已经经过代理。

页面提供安全恢复顺序：关闭客户端流量接管、恢复系统代理、确认普通网络恢复，再决定是否重新启用系统代理或 TUN。不得把修改 YAML、关闭 DNS 或同时开启多种接管方式写成通用答案。

### 4. Guide 聚合页

`/guide/` 增加两张长尾内容卡片，更新断线页摘要和日期，并把错误的 canonical 从 `/jichang/` 修正为 `/guide/`。

卡片顺序以即时问题优先：故障分流入口、订阅更新失败、已连接但无法上网，再保留现有原理和避坑内容。

## 页面共同结构

三篇排查页统一使用：

1. 编辑信息与更新时间；
2. 症状判断；
3. 两分钟快速检查；
4. 分支排查步骤；
5. 错误信息或诊断信号对照表；
6. 安全恢复与停止条件；
7. 可见 FAQ；
8. 官方资料来源；
9. 相关排查与客户端教程。

不为视觉效果引入新框架或脚本。优先复用现有文章卡片、提示框和响应式表格表达；如需共享样式，类名应以故障排查语义命名，不复用套餐表语义。

## 证据与编辑边界

技术原理优先使用：

- Mihomo 官方全局配置文档，用于运行模式、日志和 IPv6 等概念；
- Mihomo 官方 TUN 文档，用于解释 TUN、自动路由和 DNS 劫持的职责边界；
- Clash Verge Rev 官方文档或官方仓库，用于客户端特有的系统代理、TUN、订阅和日志示例；
- 操作系统官方资料，用于系统代理恢复步骤。

第三方页面只能用于发现搜索措辞和常见症状，不作为修改 DNS、配置文件或安全设置的依据。

所有内容遵守以下边界：

- 不声称某一步骤一定解决问题；
- 不使用“解决 99%”等不可证实数字；
- 不建议直接关闭防火墙、杀毒软件或系统安全功能；
- 不默认删除配置、清空数据或重装；
- 不提供未经当前官方文档支持的万能 YAML；
- 涉及日志时提醒遮盖订阅 URL、令牌、账号、节点地址和其他凭据；
- 界面按钮名称注明不同客户端可能不同，不把 Clash Verge 的界面写成所有客户端共有；
- 存在多种可能原因时按可逆成本排序，不强行给出单一根因。

## SEO 与结构化数据

三页关键词分工：

- `/guide/frequent-disconnections/`：Clash 连不上、频繁断线、节点全部超时；
- `/guide/subscription-update-failed/`：Clash 订阅更新失败、超时、401/403、解析错误；
- `/guide/connected-but-no-internet/`：Clash 已连接但无法上网、节点有延迟打不开网页、系统代理、TUN、DNS。

每页使用独立 title、description 和 canonical，加入 Article、BreadcrumbList 和与可见正文一致的 FAQPage。不得在三页复制相同的长段落或 FAQ。

三页互相链接，并连接：

- `/guide/node-speed-differences/`
- `/tutorial/clash-verge/`
- `/tutorial/clash-meta-for-android/`
- `/tutorial/flclash/`
- `/tutorial/clash-for-windows/`，仅作为遗留客户端参考，不推荐继续安装。

## 错误处理与停止条件

文章把“继续排查”和“停止自行修改”的边界写清：

- 账号、套餐或订阅授权问题：回到商家后台或提交工单；
- 多个设备、多个网络同时失败：优先确认商家公告和服务状态；
- 日志出现配置校验错误：保留原配置，不继续盲改字段；
- 系统代理无法恢复、普通网络也不可用：停止叠加设置，先恢复操作系统网络状态；
- 需要提交日志：只提交与失败时间相邻的脱敏片段。

## TDD 与验收

实现前先在 `tests/site-audit.test.mjs` 增加失败审计，锁定：

- 两个新路径存在并进入 Sitemap；
- guide 聚合页 canonical 正确并包含三张故障排查卡片；
- 三页 title、description 和搜索意图不互相重复；
- 三页具备统一诊断结构、更新时间、可见 FAQ、官方来源和相关内链；
- 页面包含日志脱敏、安全恢复和停止条件；
- 页面不出现“关闭防火墙”“解决99%”“直接删除所有配置”等危险捷径；
- JSON-LD 可解析且与可见正文一致；
- 根路径链接、商业链接和 Sitemap 全站审计继续通过。

完成后运行：

1. `node --test tests/site-audit.test.mjs`，要求零失败、零跳过；
2. `git diff --check`；
3. 桌面和 390px 浏览器验证三篇排查页与 guide 聚合页；
4. 检查诊断表格只在自身容器滚动，整页无横向溢出；
5. 检查控制台无本批引入错误。
