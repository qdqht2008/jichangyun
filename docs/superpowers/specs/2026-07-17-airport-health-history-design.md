# 机场官网健康度历史评分设计

## 背景与目标

当前机场榜总分由官网健康度、性价比、易用性和风险安全度组成，其中官网健康度占 35%。现有监测脚本每次使用 `--write` 都会覆盖 `data/airports.json` 中的最新官网状态和分数，榜单只能参考一次监测，无法反映长期表现。

本次改动新增独立、可版本管理的官网健康度历史文件。每次人工发起监测时保存真实结果，并用历史数据计算官网健康度。性价比、易用性和风险安全度继续由人工维护，不纳入自动历史计算。

完成后，榜单既展示最新一次官网状态，也展示参与评分的历史平均分、样本数和统计区间。风险优先的排序规则保持不变。

## 范围

本次包含：

- 新增官网健康度历史数据文件；
- 让监测脚本追加历史记录而不是只覆盖最新结果；
- 根据累计期或最近 90 天历史计算官网健康度；
- 让历史平均分实际进入现有总分和排序；
- 在榜单中展示最新状态与历史评分依据；
- 增加数据校验和自动测试。

本次不包含：

- 性价比、易用性和风险安全度的历史化；
- 自动定时任务或服务端数据库；
- 节点速度、晚高峰、流媒体解锁或代理线路监测；
- 删除、压缩或自动清理旧历史记录；
- 调整现有四项评分权重或风险分组门槛。

## 架构

新增 `data/airport-health-history.json`，作为官网监测历史的独立事实记录。`data/airports.json` 继续保存机场身份、人工资料、最新官网状态和其余评分输入，避免把不断增长的历史数组混入人工维护的主数据文件。

`scripts/check-airport-health.mjs` 仍由编辑人员主动运行。一次完整监测结束后，脚本把本次每个机场的结果追加到历史文件，同时更新 `data/airports.json` 中的最新官网状态。脚本不会创建定时任务，也不会在网站运行时访问机场官网。

共享数据模块负责加载并校验两个 JSON 文件、选择有效历史窗口、计算官网健康度历史平均分，并把该平均分代入现有总分公式。`data/airports.json` 中的 `scoreInputs.websiteHealth` 保存最近一次成功写入时生成的历史平均分，作为派生缓存；历史文件仍是该分数的事实来源。`/rankings/` 使用合并后的记录渲染榜单。其他使用同一共享加载函数的页面获得一致的评分，避免榜单与机场报告出现不同总分。

## 历史数据模型

历史文件使用带版本号的顶层对象，便于未来显式迁移：

```json
{
  "version": 1,
  "records": [
    {
      "slug": "quickcloud",
      "checkedAt": "2026-07-15T00:14:42.817Z",
      "websiteHealth": 95,
      "health": {
        "reachable": true,
        "finalUrl": "https://example.com/",
        "httpStatus": 200,
        "successfulAttempts": 3,
        "medianResponseMs": 1222,
        "tlsValidUntil": "2026-10-01T21:46:42.000Z",
        "runner": "editorial-check darwin/x64",
        "error": null
      }
    }
  ]
}
```

约束如下：

- `slug` 必须对应 `data/airports.json` 中的现有机场；
- `checkedAt` 必须是合法 UTC 时间；监测脚本写入时，晚于执行时刻 5 分钟以上的时间被拒绝；
- `websiteHealth` 必须是 0–100 的有限数值；
- `health` 保存本次监测的完整事实结果，不保存人工评分；
- 每次完成的监测调用形成独立样本，同一天多次监测均参与平均；
- 脚本中断或没有完成结果的数据不生成历史样本；
- 历史记录永久保留，90 天以前的数据只退出当前评分窗口，不从文件删除。

首次历史文件只导入 `data/airports.json` 中现有的 2026-07-15 真实监测结果，不推测或补造更早历史。

## 评分规则

每个机场独立确定历史窗口。记录先按 `checkedAt` 排序，以该机场最新一次有效监测时间作为窗口终点，并计算最早与最新记录之间的历史跨度。窗口不使用访客打开页面的时间，避免没有新监测时分数自行变化或滚动窗口变空；数据陈旧程度通过页面上的最新检查时间明确展示。

```text
历史跨度不足 90 天：官网健康度 = 全部累计样本的算术平均值
历史跨度达到 90 天：官网健康度 = 最近 90 天样本的算术平均值
```

最近 90 天采用包含边界的规则：`checkedAt >= 最新有效监测时间 - 90 天` 的样本参与计算。平均分统一四舍五入到一位小数，再代入现有公式：

```text
总分 = 官网健康度历史平均分 × 35%
     + 性价比 × 25%
     + 易用性 × 20%
     + 风险安全度 × 20%
```

失败但完整结束的监测是有效事实，其 `websiteHealth` 为 0，必须参与平均。脚本错误、进程中断或数据无法校验不等同于官网不可达，不得生成 0 分样本。

当某个机场没有任何历史记录时，只对该机场回退到 `data/airports.json` 中当前的 `scoreInputs.websiteHealth`，并在展示模型中标记“暂无历史样本”。其他有历史记录的机场继续使用历史平均分，不能因为单个机场缺失历史而让整个榜单退回旧规则。

排序仍分两步：先按 `normal`、`watch`、`high` 的风险级别排序，再按包含历史官网健康度的总分降序。同分时继续按中文名称稳定排序。

## 监测写入流程

执行带写入参数的监测时：

1. 读取并校验机场主数据与现有历史数据；
2. 对所有机场完成本轮官网检查；
3. 将完整结果转换为历史样本；
4. 在内存中追加历史样本，更新机场的最新 `health`，并用更新后的历史重算 `scoreInputs.websiteHealth` 与评分依据；
5. 重新校验两个完整数据对象；
6. 通过临时文件写入并替换目标文件；
7. 任一步骤失败时以非零状态退出并明确报告失败阶段。

历史记录使用监测时间和机场 slug 形成稳定标识。完全相同的 `slug + checkedAt` 被视为重复记录并拒绝写入；同一天但时间不同的监测是独立样本。

两个 JSON 文件无法获得真正的跨文件事务语义，因此脚本必须先完成全部内存计算与校验，再缩短替换文件之间的时间，并在替换失败时显式报错。下一次运行前的加载校验会暴露不一致，不能静默继续。实现不引入数据库或复杂日志系统来掩盖这一静态文件限制。

不带 `--write` 时，脚本继续只输出本轮结果，不修改机场数据或历史文件。

## 榜单展示

每张榜单卡片保留最新一次监测状态，包括可达性、成功次数、响应时间和检查时间。在官网健康度位置增加历史口径：

- 历史平均分，保留一位小数；
- 有效样本数；
- 实际统计起止日期；
- 累计不足 90 天时标注“累计平均”；
- 达到 90 天后标注“近 90 天平均”；
- 没有历史记录时标注“暂无历史样本”，并说明使用当前值。

页面继续明确：官网健康度只反映公开入口在记录时点的可达性、HTTPS 和响应时间，不代表代理节点、线路速度、晚高峰或解锁能力。

本次只补充评分依据，不重做卡片布局、不增加图表，也不增加历史详情页。

## 失败处理

- 历史文件请求失败、JSON 无法解析或整体结构不合法时，榜单显示“历史数据载入失败”并停止评分榜单渲染，不静默退回单次评分；
- 单个机场没有历史记录属于合法的不完整数据，按单机场回退规则处理；
- 未知 slug、非法日期、未来时间、非有限分数、越界分数和重复稳定标识必须被校验拒绝；
- 历史记录的物理顺序不影响计算，代码始终按时间排序；
- 监测失败与脚本失败严格区分：前者生成 0 分事实样本，后者不生成样本；
- 任一写入或替换失败都必须以非零状态退出，不能宣称监测已保存。

## 测试与验收

自动测试必须表达业务意图并覆盖：

- 历史跨度不足 90 天时使用全部累计样本；
- 历史跨度达到 90 天时只使用包含边界日在内的最近 90 天样本；
- 完整失败监测的 0 分会降低历史平均分；
- 同一天多次监测作为多个独立样本参与平均；
- 输入顺序不影响历史窗口和平均分；
- 单个机场无历史记录时只回退该机场；
- 历史平均分实际进入总分和同风险组内排序，而非仅用于展示；
- 追加监测保留既有记录，不覆盖旧历史；
- 完全相同的 `slug + checkedAt` 被拒绝；
- 未知 slug、非法日期、未来时间和非法分数被拒绝；
- 不带 `--write` 时两个数据文件均不改变；
- 榜单展示最新状态、历史平均分、样本数和统计区间；
- 历史文件整体加载失败时显式失败，不静默降级；
- 现有机场数据、风险优先排序、筛选和全站审计测试继续通过。

浏览器验收覆盖桌面端与 390×844 移动视口：榜单能正常加载，历史说明可读且不造成横向滚动，最新状态与历史平均不会混淆，控制台没有本站未处理异常或静态资源 404。

## 完成标准

只有以下条件全部满足后才能宣称完成：

1. 历史文件仅包含真实监测结果，并以现有 2026-07-15 数据初始化；
2. 新监测可以追加历史，同时保留旧记录；
3. 未满 90 天与达到 90 天后的两种平均规则均由确定性代码实现并测试；
4. 历史平均分确实影响榜单总分和排序；
5. 页面清楚展示最新状态、平均口径、样本数和统计区间；
6. 所有自动测试实际运行且零失败、零跳过；
7. 桌面和移动浏览器验收完成，无法执行的检查必须显式报告；
8. 工作区只包含本功能授权的改动，并保留用户现有 `.DS_Store` 修改。
